# 5분 발표 대본

슬라이드 9장. 목표 시간 4분 45초(25+35+35+35+25+35+40+20+35초), 15초 여유. 이 시간은 배분 계획이며 실제 발화 측정값이 아니다. 본인 목소리로 리허설하며 확인한다. 준비시간 포함 최대 6분. 수치는 `결과보고서.md` 기준.

## 1. 운영 장애 진단 에이전트의 근거 기반 검증·검색·조사 안정성 개선

[25초] 운영 장애 진단 에이전트를 개선했습니다. 기존에는 답변이 길고 번호만 있으면 통과했고, 세 번 실패하면 강제로 합격했습니다. 운영자가 잘못된 수치를 믿고 조치할 수 있다고 생각해, 수집 근거와 답변을 대조하는 것을 중심 주제로 잡았습니다. 검색과 조사 실패 처리도 함께 개선했습니다.

## 2. 기능 개선: 검증 · 검색 · 실패 처리

[35초] 흐름은 조사, 작성, 검증입니다. 시스템별 CPU와 메모리 수치를 비교하고, 틀린 항목을 구체적으로 알려 다시 작성하게 합니다. 세 번 실패하면 답변 대신 확인된 자료와 실패 이유를 제공합니다. 매뉴얼은 의미로 검색하되 확신이 낮으면 선택하지 않고, 조사 하나가 실패해도 성공한 자료는 유지합니다.

## 3. 구조·안정성 개선과 스스로 찾은 약점

[35초] 모니터링과 매뉴얼 조사를 두 서브에이전트로 나누고, 그래프의 각 역할을 모듈로 분리했습니다. 없는 시스템을 다른 시스템으로 바꾸지 않도록 대상 해석도 고쳤습니다. 마지막 점검에서는 비슷한 이름을 혼동하는 문제와, 미조회 시스템의 숫자가 다른 시스템과 같으면 통과하는 문제를 찾아 수정하고 회귀 테스트를 추가했습니다.

## 4. 사용한 기술: 제공 기반과 내 변경

[35초] 제공된 기반은 LangGraph 흐름, 서버와 세션, 병렬 조사입니다. 제가 개선한 부분은 검증과 실패 분기, 조사 분리, 검색 도구, 모듈화와 테스트입니다. MCP는 Model Context Protocol로 도구 연결 규약이고, RAG는 Retrieval-Augmented Generation으로 검색 자료를 답변에 활용하는 방식입니다. 두 서브에이전트는 독립적으로 추론하는 모델이 아니라 도구 호출형 그래프입니다.

## 5. 최종 실행 화면

[25초] 수정 후 로컬 서버에서 다시 확인한 화면입니다. 작성 모델은 모의 모델이고 모니터링과 검색 도구는 실제로 연결했습니다. 수집값과 답변값이 같은지 비교표로 보여줍니다. 정상, 세 번 검증 실패, 자료 부족으로 작성 생략하는 흐름을 모두 확인했습니다.

## 6. 선택 전후 비교 화면

[35초] 이 비교 화면은 같은 질문에 CPU 값을 의도적으로 높여 쓰게 한 재현 실험입니다. 기존 검증은 틀린 값을 최종 답변으로 내보냈고, 개선 검증은 세 번 실패하면 중단합니다. 핵심은 실패를 숨기지 않고 불일치 이유와 실제 수집값을 보여주는 것입니다. 실모델의 오류 빈도를 측정한 실험은 아닙니다.

## 7. 전후 수치 비교

[40초] 기존 17개 사례에서 오류 차단은 9개 중 2개에서 9개로 늘었고 정상 8개는 통과했습니다. 추가 표적 평가도 개선됐지만 직접 만든 사례라 일반화에는 한계가 있습니다. 검색은 14개 중 기대 일치가 6개에서 12개로 늘었습니다. 최신 실모델 비교에서는 작성 시도는 양쪽 모두 평균 1회였고, 시간도 비슷해 속도 향상은 주장하지 않습니다.

## 8. 보너스: 실측 수치 3가지

[20초] 근거가 하나도 없을 때 작성 모델을 호출하지 않도록 했습니다. billing-service 단일 질문에서 작성 호출이 1회에서 0회로 줄었습니다. 병렬 실행과 모델 분리 수치도 측정했지만, 각각 모의 지연과 가정 단가를 사용하므로 실제 운영 성능이나 실과금 절감으로 주장하지 않습니다.

## 9. 한계와 트레이드오프

[35초] 이 검증기는 추출한 시스템별 수치만 대조합니다. 원인 설명과 권장 조치가 맞는지는 판단하지 못하고, 새로운 표현을 놓칠 수도 있습니다. 초안을 숨겨 안전성을 높이는 대신 답변이 조금씩 생성되는 경험은 포기했습니다. 제 개선의 의미는 모든 답변을 맞히는 것이 아니라, 확인한 범위를 보여주고 근거가 부족할 때 멈추도록 만든 데 있습니다. 감사합니다.
