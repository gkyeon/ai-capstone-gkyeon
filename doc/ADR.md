# 설계 결정 기록 (ADR)

## ADR-01: 수치 검증은 규칙 기반으로 분리
- 문제: 형식만 검사하고 3회 실패를 강제 통과시켰다.
- 고려 대안: 프롬프트 강화, 추가 언어 모델 판정, 직접 수치 대조. 대안 전체를 실험하지는 않았다.
- 결정: 시스템·CPU·메모리 수치 대조를 verifier.py에 분리. 0.5%p 오차 허용, 총 3회 실패 시 종료.
- 이유: 직접 비교 가능한 항목에 추가 모델 호출 없이 구체적인 피드백을 제공한다.
- 비용: 문장 표현·시스템 연결 규칙에 따른 오탐과 누락. 원인 설명은 검증하지 않는다.

## ADR-02: 소규모 로컬 의미 검색
- 문제: 기존 알림 키워드 분류는 한국어 증상을 놓치면 db-down을 기본 선택했다.
- 고려 대안: 한국어 키워드 사전 확장, 언어 모델 분류, 문서 임베딩 검색. 키워드 사전 확장과 별도 모델 분류는 실험하지 않았다.
- 결정: qwen3-embedding:0.6b와 6개 매뉴얼의 코사인 유사도 검색을 MCP 도구로 제공. 문서 본문을 검색하고 선택 문서를 기존 작성 단계에 전달한다.
- 이유: 표현 차이를 처리하면서 후보·점수·문서 출처를 제시할 수 있고, 로컬 실행을 유지한다.
- 범위: 6개 짧은 문서여서 문서 단위 인덱스와 메모리 캐시로 시작한다. 외부 벡터 DB와 청크 분할은 보류.
- 보류 정책: 점수 0.45 미만 또는 상위 두 후보 점수 차이 0.025 미만이면 미확정. 이 값은 설계 기본값이며 최적성이나 보정 확률을 뜻하지 않는다.
- 비용: 로컬 Ollama와 639MB 모델 설치 필요, 초기 임베딩 시간, 의미가 가까운 장애 간 오선택, 재시작 시 인덱스 재계산.
- 검증: 자체 14개 구성요소 평가에서 기대 일치 6/14→12/14. 미확정 1개·오선택 1개. 개발자 작성 평가로 일반 성능을 보장하지 않는다.

## ADR-03: 병렬 조사 실패 격리
- 문제: asyncio.gather의 단일 예외가 성공 결과의 반환도 막았다.
- 결정: 작업별 예외를 수집하고 성공 자료를 보존한다. 실패 대상을 이벤트와 최종 안내에 표시한다. 전체 모니터링 자료가 없으면 기존 검증 불가 경로로 종료한다.
- 이유: 부분 자료라도 제공하되 조사 완결성을 과장하지 않는다. unknown 상태의 기본값 0은 관측값으로 취급하지 않는다.
- 비용: 부분 결과가 완전한 진단처럼 보일 위험이 있어 안내가 필요하다. 실패 원인별 세밀한 정책은 후속 과제다.
- 검증: 일부 실패·전체 실패·매뉴얼 탐색 실패·검색 실패 시나리오. 취소 신호는 전파한다.

## ADR-04: 초안 비공개와 설명 가능한 화면
- 문제: 반려된 초안이 화면에 남아 사용자가 신뢰할 위험이 있었다.
- 결정: 서버와 화면 양쪽에서 초안 토큰을 차단한다. 진행 단계는 유지하고 최종 답변·수치 비교표·검색 후보·검증 범위를 제공한다.
- 비용: 답변 본문은 완료 후 나타난다. 진행 상황이 대기 시간을 설명하지만 실제 지연을 없애지는 않는다.
- 검증: 실제 서버와 모의 작성 모델, 실제 임베딩 검색으로 실행. 데스크톱·모바일 배치 확인.

## 제공 기반 구조 결정 (ADR-05~09)
아래는 과제 원본 zip에 이미 있던 구조다. 직접 설계한 것이 아니므로 "이유"는 코드 주석과 구조에서 읽은 것이며, 원작자의 의도를 확인한 것이 아니다. 우리가 한 일은 이 구조 위에서 측정하고 일부를 확장한 것이다.

## ADR-05: 선형 호출 대신 LangGraph 상태 그래프 (제공 기반)
- 결정: route→plan→gate→research→replan_check→analysis→write→validate→finalize를 `StateGraph` 노드와 조건부 엣지로 구성. v1(선형)은 `SUPERVISOR_VERSION=v1`로 롤백용 보존(`supervisor_v1.py`).
- 이유(코드에서 읽은 것): 분기(chat/incident), 재조사 루프, 검증 후 재작성 루프를 노드·엣지로 명시할 수 있다.
- 우리의 확장: validate의 실패 종료 경로(`finalize_failed`)와 `should_replan`/`is_sufficient` 분리.
- 비용: 흐름이 코드 곳곳의 분기 함수에 퍼져 있어 한눈에 읽기 어렵다. 별도 Worker 에이전트가 아니라 한 그래프 안의 역할별 노드다.

## ADR-06: 진행 상황은 SSE로 단방향 스트리밍 (제공 기반)
- 결정: `/chat/stream`이 노드별 이벤트를 `text/event-stream`으로 전송하고, 화면은 `EventSource`로 수신.
- 이유: 서버→화면 단방향이면 충분하고, 응답이 오래 걸릴 때 진행 단계를 보여줄 수 있다.
- 우리의 변경: 반려될 수 있는 초안 토큰(AnswerToken)은 서버와 화면에서 차단(ADR-04). 토큰 단위 스트리밍을 포기하고 신뢰성을 택했다.
- 비용: 답변 본문이 완료 후 한 번에 나타난다. 원래도 Ollama·OpenAI 작성 단계는 토큰 단위 중계가 아니었다.

## ADR-07: 세션 상태는 프로세스 밖 SQLite에 저장 (제공 기반)
- 결정: 대화 이력을 `session.db`에 `thread_id`별로 저장하고 요청마다 로드. 프로세스 안에 사용자별 상태를 두지 않는다.
- 이유: 서버를 재시작해도 이력이 유지된다(코드 주석).
- 한계: MCP 클라이언트·그래프는 프로세스 싱글턴이다(사용자 상태는 아님). 단일 SQLite 파일이라 다중 서버 확장에는 부적합하다.

## ADR-08: 모델을 fast/quality로 분리 (제공 기반, 우리는 측정)
- 결정: 분류·계획은 저비용 fast 모델, 최종 답변 작성은 quality 모델.
- 측정(`eval/bonus-measure-20261021.md`): 같은 토큰을 분리 단가와 전부 quality 단가로 계산했을 때 약 59% 절감(추정). 토큰은 글자수/4 추정, 단가는 가정값, fake 응답 기준.
- (재작성 횟수에 민감한 추정이다: 서브에이전트 분리 직후에는 약 47%였으나 검증 오탐 수정으로 불필요한 재작성이 줄어 현재 약 59%.) 한계: Ollama 로컬 실행은 실제 과금이 없고, 프롬프트 압축은 하지 않는다(대화 이력 최근 10개 제한만 있음).

## ADR-09: 조사는 동시 실행 (제공 기반, 우리는 측정)
- 결정: research 노드가 모니터링·매뉴얼 조회 태스크를 `asyncio.gather`로 동시 실행.
- 측정: 모니터링 3개 조회 라운드가 병렬 0.36~0.37초, 직렬 1.07~1.08초(약 3배). 단 태스크당 0.35초 고정 지연은 원본의 시뮬레이션이라 구조 효과만 의미한다.
- 우리의 확장: `return_exceptions=True`로 일부 실패를 격리(ADR-03).

## ADR-10: research를 monitoring/runbook 서브에이전트로 분리 (직접 변경)
- 문제: `research_node` 안의 `run_one` 한 함수가 모니터링 조회, 의미 검색, 기존 URI 조회를 모두 처리해 책임이 섞여 있었다.
- 고려 대안: 그대로 두기 / 함수만 분리 / 컴파일된 LangGraph 서브그래프로 분리 / PDF 예시처럼 로그·메트릭·런북 3개로 분리. 함수만 분리하는 안과 3개 분리 안은 구현·비교하지 않았다. 로그 분석 데이터가 이 프로젝트에 없어 2개로 분리했다.
- 결정: `agent/subagents.py`에 `monitoring_agent`(도구 호출·재시도·15초 제한→관측값 검사)와 `runbook_agent`(의미 검색 60초 / 기존 조회 15초)를 서브그래프로 만들고, `research_node`는 supervisor로서 작업 종류별 분배·병렬 실행·결과 취합만 한다. 어느 에이전트가 처리했는지 `TaskCompleted` 이벤트에 기록한다.
- 이유: 역할별로 입력·출력·실패 지점이 분리되고 단위 테스트가 쉬워진다. 병렬 실행과 부분 실패 격리(ADR-03·09)는 supervisor의 `gather`가 그대로 유지한다.
- 비용·한계: 두 에이전트는 LLM이 판단하는 에이전트가 아니라 도구를 호출하는 작업자이며, 서로 대화하거나 협상하지 않는다. 성능 이득은 없다(전체 그래프 시간 0.73→0.74초, 서브그래프 호출 오버헤드 약 0.01초, fake 모델·실제 MCP 5회 측정). 이득은 구조의 명확성이며 수치로 증명하지 않았다.
- 검증: `eval/test_subagents.py`, 기존 `test_expansion.py`·`test_verification_features.py` 통과, 실제 MCP 서버 연동 측정에서 병렬 0.36초 유지.

## ADR-11: 대상 시스템은 코드가 해석하고 폴백을 숨기지 않는다 (직접 변경)
- 문제: 질문에 목록에 없는 시스템(예: billing-service)이 있으면 실모델 계획 정규화(`_guess_target`)가 이를 조용히 `auth-service`로 바꿨다. 사용자가 묻지 않은 시스템에 대한 "근거 있는" 답변이 만들어진다. fake 모델 경로에서도 `Payments_Service`처럼 표기가 다르면 auth-service로 빠졌고, `payments-service-3`(인스턴스 표기)은 별도 시스템으로 조사해 실패했다.
- 고려 대안: 모델 프롬프트로만 해결 / 코드 해석 / 사용자에게 되묻기. 되묻기(대화형 확인)는 구현하지 않았다.
- 결정: `agent/targets.py`가 known(표기 차이 무시, 인스턴스는 소속 시스템)·unknown(시스템 이름 꼴인데 목록에 없음)·defaulted(이름이 전혀 없음)를 구분한다. 계획 노드는 모델이 빠뜨린 대상을 조사 작업으로 추가하고(권위 게이트), unknown은 바꾸지 않고 조회 실패로 드러나게 한다. 이름이 없을 때만 기본값(auth-service)을 쓰고 `TargetResolution` 이벤트와 최종 답변 첫머리에 알린다.
- 측정(`eval/eval_targets.py`, 사례 8개, 계획 정규화는 스텁 모델 출력 기준): 목록에 없는 시스템의 조사 대상이 auth-service로 바뀌던 사례(A1·A8)가 질문의 이름 그대로 남고, 혼합 질문(A2)에서 사라지던 billing-service가 복구된다. 대소문자·밑줄(A6)과 인스턴스(A7) 표기는 올바른 시스템으로 해석된다. 이전에 검증 실패로 끝나던 정상 질문 2개(A5·A7)가 통과하고(검증기 개선 ADR-12의 효과 포함), 다른 시스템을 조용히 조사해 통과하던 A6이 올바른 시스템(payments-service)을 조사한다.
- 비용·한계: 시스템 이름 꼴(`...-service`, `...-숫자`) 정규식에 의존해 다른 형태의 이름은 unknown으로도 잡지 못한다. 기본값 auth-service는 그대로 두었고 알리기만 한다. 되묻기가 아니라 알림이다. 계획 모델(실모델)이 실제로 그런 출력을 내는지는 스텁으로 가정했다.

## ADR-12: 검증기 2차 — 표현 범위 확대와 시스템명 요구 완화 (직접 변경)
- 문제: 실모델 재작성의 대부분이 `no_system`(시스템명 누락, 수치 없는 답변 포함)이었고 그만큼 시간이 늘었다. 이미 알려진 약점(한글 동의어·숫자가 먼저 오는 문장·표·부정문·'각각'·임계치 인용)도 남아 있었다. 정상 질문의 런북 문장("CPU 90% 이상 지속 시")이 직전 시스템의 수치로 오인되어 검증 실패로 끝나는 오탐도 확인했다.
- 결정(`agent/verifier.py`): ① 지표 동의어(프로세서·중앙처리장치·utilization 등)와 '퍼센트/percent' 표기 ② '99%의 CPU'(숫자 먼저)와 마크다운 표(열 단위), '각각 a, b'(앞 시스템 순서 대응), 'CPU usage of X is n%' ③ 임계치·조건문("임계치 80%", "90% 이상 지속 시", "90%를 넘기면")과 부정된 수치("85%가 아니라")는 측정값 주장에서 제외하되 부정 뒤의 긍정 수치("…아니라 99%")는 대조 ④ 시스템명은 수치를 인용했는데 어느 시스템인지 모를 때만 요구 ⑤ 조사했지만 자료를 얻지 못한 시스템("조회하지 못했다")은 언급을 허용하고 그 수치를 주장하면 반려.
- 평가: 구현 전에 사례를 먼저 작성하고 개선 전 검증기를 스냅샷(`eval/baseline/verifier_before_v2.py`)으로 보관해 같은 사례로 비교했다(`eval/eval_verifier_v2.py`). 표적 회귀 28개: 정상 통과 7/14 → 14/14, 오류 차단 6/14 → 14/14. 설계 시 보지 않은 변형 6개: 정상 1/1 → 1/1, 오류 4/5 → 5/5. 자체 점검에서 찾은 부작용·회귀 탐침 8개: 정상 1/4 → 4/4, 오류 3/4 → 4/4.
- 정직한 한계: 표적 회귀는 지목한 약점 유형에서 가져온 사례라 독립 평가가 아니고 수치가 낙관적이다. 변형 6개 중 `CPU utilization of X: n%`(U2)는 구현 중 같은 영어 패턴(T-B11)을 보고 규칙을 넣어 해결된 것이므로 일반화의 증거로 쓰지 않는다. 임계치·조건문 제외 규칙은 처음에 "99% 이상 지속되고 있습니다"·"99%를 넘었습니다"·"91.4%가 아니라 99%" 같은 **틀린 측정값을 통과시키는 부작용**을 냈고(자체 점검에서 발견), 조건문 어미(지속 시·이면·넘으면)만 제외하도록 좁히고 부정 뒤 수치를 따로 대조하도록 고쳤다. 그런데 좁힌 패턴이 실제 런북 문장 "CPU가 90%를 넘고 지속되면"을 놓쳐 오탐이 재발했고(대상 시스템 평가를 다시 돌려 발견), 이 문장을 사례 V8로 추가해 '넘고 지속되면'을 제외 목록에 넣었다. 규칙 기반이라 새 표현은 여전히 놓칠 수 있다. 시스템명 요구를 완화한 대가로 수치 없는 답변은 어느 시스템 얘기인지 확인하지 않고 통과한다(보고표에 "대조한 수치가 없음"이 표시된다).

## ADR-13: 그래프 노드를 역할별 모듈로 분리 (직접 변경, 동작 변경 없음)
- 문제: `graph.py` 한 파일(425줄)에 상태 정의, 10여 개 노드, 분기 함수, 그래프 조립이 섞여 있었다.
- 결정: `agent/state.py`(상태·비용 헬퍼)와 `agent/nodes/`(routing·planning·research·writing·validation·finalization)로 나누고, `graph.py`(58줄)는 `build_graph`와 기존 이름의 재노출만 맡는다. 노드는 `SupervisorDeps`를 주입받는 함수라는 규칙을 유지했다.
- 검증: 이동 전후 `test_subagents`·`test_expansion`·`test_verification_features`·`measure_bonus`(병렬 0.36~0.37s 대 직렬 1.07~1.08s 유지)·실제 서버 `/chat/stream`을 모두 확인했다. 미정의 이름은 AST 점검으로 확인했다.
- 한계: 파일 수가 늘어 흐름을 따라가려면 `graph.py`의 import 목록을 먼저 읽어야 한다. 성능 이득은 없고 구조의 명확성과 테스트 용이성이 이득이며 수치로 증명하지 않았다. 병렬 측정 스크립트가 `asyncio`를 교체하는 위치가 `agent.nodes.research`로 바뀌었다.

## ADR-14: 근거가 없으면 작성 모델을 호출하지 않는다 (직접 변경, 비용 최적화)
- 문제: 조사했지만 모니터링 자료가 하나도 없는 질문(예: 목록에 없는 billing-service)에서도 비싼 작성(quality) 모델이 먼저 호출됐고, 그 답변은 어차피 검증할 수 없어 "자료 부족"으로 끝났다.
- 결정: `analysis`와 `write` 사이에 `evidence_gate` 노드를 두고, 모니터링 근거가 0건이면 작성을 건너뛰고 곧바로 `finalize_failed`(자료 부족·검증 불가)로 보낸다. `legacy` 검증 모드(개선 전 비교용)는 건너뛰지 않는다. 화면에는 "모니터링 자료가 없어 답변 작성을 생략"으로 표시한다.
- 측정(Ollama, billing-service 질문 3회, `eval/ollama-live-evidence-gate-20261021.json`): 응답 시간 36.6초 → 1.2~2.7초, 작성 모델 호출 1회 → 0회, 추정 비용 $0.005765 → $0.000085. 개선 전 값은 같은 질문을 같은 모델로 돌린 이전 실행(`ollama-live-20261021-r2*.json`)이며, 그 두 실행은 시간·비용이 같았다. 단일 질문이라 일반화는 하지 않는다.
- 한계: 조기 종료는 "모니터링 근거가 0건"일 때만 동작한다. fake 모델은 연관 시스템(web-01)을 항상 함께 조사해 근거가 생기므로 이 경로가 열리지 않는다(`eval/test_evidence_gate.py`는 모킹으로 0건을 만들어 확인). 근거가 일부라도 있으면 기존대로 작성한다. 매뉴얼만 있고 모니터링이 없는 경우도 조기 종료한다. 비용은 토큰 글자수 추정 기반이다.

## ADR-15: 의미 검색이 만든 비용·지연을 측정해 둔다 (측정)
- 문제: 임베딩 검색 도입은 정확도를 얻는 대신 비용·지연·의존성을 만든다. 이를 수치로 확인하지 않았다.
- 측정(`eval/measure_embedding.py`, 매뉴얼 6개): 콜드 첫 검색 약 1.1초(임베딩 모델만 올린 상태), 인덱스 재구축 약 0.28초, 웜 검색 약 29ms(최대 37ms), 기존 키워드 분류기 약 2µs, 모델 디스크 639MB. 실서버 첫 요청에서 작성 모델과 메모리를 나눠 쓸 때는 9.64초가 관찰됐다.
- 해석: 웜 상태의 검색은 에이전트 전체 응답(수십 초)에 비해 작다. 지불하는 것은 콜드 시작 지연, 로컬 모델 639MB와 Ollama 의존성, 프로세스 재시작 시 인덱스 재계산이다. 6개 문서라 외부 벡터 DB는 쓰지 않았고, 문서가 많아지면 메모리 캐시·재구축 비용을 다시 봐야 한다.

## 표현 원칙

- 테스트에서 확인한 것과 설계상 기대하는 것을 구분한다.
